# 线程按进程 / IO 流展示

验证日期：2026-09-29。

线程页提供“按进程 / 按 IO 流”切换，默认按进程。两种视图共用所选轮次、所选 3 秒区间及原始指标，切换分组不改写数据。切到 CPU / NUMA 或时延 / 深度后再返回，保留区间与分组方式。整轮汇总采用当前分组方式。

## 按进程

逐线程记录按主机、进程角色和 PID 分组；同主机同名但不同 PID 的进程分别展示。组内按线程池、线程名自然排序，再按 TID / starttime 排序。不同线程的 starttime 不作为进程分组标识。

组头显示已采集线程的 CPU 合计，可跨核超过 100%；任一已采集线程 CPU 缺失时合计为“—”，不补零。该值仅代表采集到的线程，不宣称系统完整进程 CPU。整轮线程池原始数据没有 PID，只按主机及进程角色汇总，并明确标注未分 PID。

## 按 IO 流

1. VM fio。
2. NFS 协议层：QEMU vCPU → main / main-loop → NFS poller → asan-stord glfs-nfs / nfs-rpc。
3. 业务入口：gfapi-opt（IOR）→ gfapi-core（路由、AFR）。
4. 本地数据分支：DATA glfsd-net → tierd-core → tierd-aio。
5. 远端数据分支：同序。本地与远端是并行分支，展示先后不表示串行执行。
6. 完成返回：本地 / 远端 DATA libcomm → 本地 gfapi-net。
7. 明确标为仲裁的控制线程。
8. 未映射角色。

只展示实际采集的线程及分组。每条线程记录只归一个组；同线程参与请求与返回时不复制指标。组内先按角色顺序，再按自然线程名与 PID / TID / starttime 稳定排序，负载变化不改变行位置。CPU、IPC、SMT 及调度详情仍来自所选轮次、所选 3 秒区间。

DATA / 仲裁由分支及进程角色声明识别；未明确类型的 glusterfsd 保留在未映射组。兼容实际采集角色 stord、qemu、glusterfsd 与模拟别名 asan-stord、main-loop。vhost / iSCSI 的协议前端顺序尚待提供，IOR 后共用数据与完成分组。

## 扩展

进程分组位于 `processThreadGroups.ts`，IO 角色映射位于 `ioThreadOrder.ts`。补充已确认的角色别名及阶段映射后，分窗表与整轮汇总同步生效。网卡 IRQ / softIRQ 仍通过 CPU / NUMA 和网络页面观察，不作为业务线程伪造。

## 验证

- 前端 29 项检查通过：既有分窗对齐与 CPU 覆盖 12 项、IO 角色与排序 9 项、进程分组与 CPU 合计 8 项。TypeScript 与 Vite 构建通过。
- 最新高深度随机写模拟批次、正式 21–24 秒：两种视图均为 15 条线程，CPU 端点、CPU%、IPC、SMT 和调度详情逐条一致，仅排序与分组不同。
- IO 视图的本地、远端分支均先 glfsd-net 后 tierd-core；未采集的层及线程不生成占位指标。
- 进程视图区分本地 / 远端及 PID，模拟数据按其原始 PID 划分六组。整轮数据没有 PID，按五个主机 / 进程角色组展示，并标明未分 PID。
- 切换上次轮次、切至 CPU / NUMA 再回到线程，仍保留正式 21–24 秒、“上次线程”与“按进程”。整轮汇总随两种模式同步切换。
