# 版本内性能排查：随 fio 留证据，发现退化后对比

## 本次确认的范围

版本内指大部分代码已经完成，后续以小改动为主，例如是否切线程、绑核、软亲和。按用户经验，优先排查 CPU 执行瓶颈、调度抢占、跨 NUMA 和网络中断处理瓶颈。

固定前提：CPU、内存、服务器、网卡及其他设备完全固定；本轮与上一次比较使用同一个 fio 模型。默认比较对象就是上一次该场景的测试记录。版本内排查围绕两轮之间的代码、参数调整及运行行为变化展开。

第一步是建立每次性能测试的可比较记录。Agent 从记录中指出哪里发生变化、有哪些支持或反对证据，以及下一步如何验证；最终根因仍由针对性实验确认。

本文包含采集和分析设计。当前已实现版本批次导入、自动配对、证据规则分析、专家评价，以及 Linux 本机采集与合并入口。页面默认数据明确标为模拟；Linux 采集尚未在用户集群运行，不能将示例判断作为实测结论。

当前采集入口读取线程 CPU、调度统计、允许 CPU 集合、进程 NUMA 页、逐 CPU 与网卡 IRQ，并保存 perf 原始计数和短窗口栈文件。真实函数热点解析、产品软亲和、阻塞栈和竞争进程归因仍需适配器补充，详见 [Linux 采集说明](../collectors/README.md)。下文的完整采集目标按此边界逐步实现。

## 一次场景测试保存什么

全量测试包含多个场景；每个场景、每次重复分别生成 run_id，并关联到同一测试批次。

- **测试结果**：fio 原始 JSON、IOPS、带宽、时延分布、完成 IO 数、实际深度分布；保存 jobfile 和版本。
- **固定环境档案**：一次保存 CPU、内存、服务器、网卡、SMT/NUMA 拓扑及 IO 角色映射，每轮引用同一档案。
- **本轮版本与运行记录**：构建/代码标识、改动摘要、业务参数、内核与 perf 版本；产品软亲和配置、OS 允许 CPU 掩码、实际落核与内存 NUMA 分布分别保存。固定硬件上仍需观察实际调度与内存局部性。
- **线程与 CPU 时间线**：IO 链路线程的用户态/内核态 CPU 时间、运行 CPU、迁移、上下文切换、可用的运行队列等待统计；宿主机每 CPU 的用户态、内核态、IRQ、softIRQ、空闲及其他竞争者概况。保留物理核与 SMT 兄弟关系。
- **perf 计数与采样**：cycles、instructions、task-clock 等基本计数，同一稳态窗口的函数栈采样和原始文件；按能力增加缓存、TLB、NUMA 相关事件。PMU 事件、用户/内核/guest 范围、符号与 build ID、计数运行比例、丢样和采集失败都入档。
- **网络证据**：两台数据主机对应网卡的队列、IRQ 配置与实际每 CPU 活动、软中断 CPU 时间及 NET_RX/NET_TX 次数、ksoftirqd/NAPI 相关热点、包量、丢包、重传、吞吐、RSS/RPS/XPS 和 irqbalance 状态。次数与耗时分别记录。

每轮自动发现 PID/TID。以主机角色、卷/VM、IO 分支、进程角色和线程池角色进行跨轮对齐；记录具体 PID/TID 与生存期作为本轮实例。线程池同时比较总 CPU 成本、线程数、最忙线程和落核分布，不能只看平均值。

已知 IO 链路的关键线程均保留基本指标，包括 CPU 很低但在等待的线程；同时发现新增热点与链路之外的 CPU 竞争者。

## 按现有 IO 流覆盖采集对象

以下角色来自原始 IO 文档；PID/TID 不写成长期配置。

| 区域 | 初始采集对象 | 目的 |
| --- | --- | --- |
| VM | fio 工作线程、guest CPU 与块 IO 完成上下文 | 对齐测试结果，识别 VM 内等待 |
| 本地协议前端 | QEMU vCPU、主线程、NFS poller；asan-stord 的 glfs-nfs 池 | 分辨协议处理与唤醒/切线程开销 |
| IOR 及共享业务链路 | gfapi-opt、gfapi-core、gfapi-net 等池 | 分析业务处理、分发和结果返回 |
| 本地数据分支 | DATA glusterfsd 的 glfsd-net、libcomm；tierd-core、tierd-aio | 分析 VSSHM、本地存储处理与等待 |
| 远端数据分支 | 远端 DATA glusterfsd 的 glfsd-net、libcomm；tierd-core、tierd-aio | 分析 TCP 分支及远端处理与等待 |
| 网络处理 | 两端网卡队列、hardIRQ、softIRQ/NAPI、相关内核线程 | 分析网络处理落核、负载集中和业务线程竞争 |
| 仲裁控制 | 本次卷相关的仲裁进程/线程 | 保留锁、changelog、xattr 等控制操作证据；不是第三份数据副本 |

NFS 示例的 QEMU → asan-stord 使用同机 Unix socket，不经过物理网卡。写的远端 TCP 分支需要单独插入网络观察点，并关联 AFR 结果汇合。采集同时覆盖两台数据主机的发送与接收/完成路径。不能因本地线程正常就排除远端问题。

页面提供“按进程 / 按 IO 流”两种展示，默认按主机、进程与 PID 分组；整轮线程池数据没有 PID 时按进程角色汇总。IO 流视图依次展示 guest fio → 协议前端（vCPU、QEMU main、NFS poller、glfs-nfs）→ IOR（gfapi-opt、gfapi-core）→ 本地 DATA 与远端 DATA 各自的 glfsd-net、tierd-core、tierd-aio → 完成返回（两端 DATA libcomm、本地 gfapi-net）。本地和远端是并行分支，展示次序不表示串行执行。仲裁控制及未映射角色单列；DATA 与仲裁角色无法确认时保持未映射。同一线程的请求和完成共用完整区间计数，不拆成阶段 CPU。vhost、iSCSI 前端顺序待产品补充，IOR 后复用共享分组。

## 怎样比较，而不误判

直接将本轮与上一次同场景测试并排对比，环境和 fio 模型采用上述固定前提。先观察 fio 下降发生在哪个窗口，再关联线程 CPU、等待、perf、NUMA 和网络处理变化。绑定、软亲和、线程池、IRQ 配置及代码改动作为本轮差异展示；缓存/预热状态与后台负载用于解释运行波动。

- IPC = instructions / cycles；线程池使用同窗口计数总和的比值，不直接平均各线程 IPC。
- 同时计算每个线程角色/线程池的 CPU 时间/逻辑 IO、instructions/逻辑 IO、cycles/逻辑 IO，分母使用对应采样窗口内 guest fio 的完成数。固定吞吐窗口也可使用每 MiB 成本。
- 本地和远端分别展示。guest 和 host 属于不同观察层，不能简单相加；共享进程或 CPU 的后台负载也不能全部归因于本次 fio。
- CPU 时间低需分清没有工作、阻塞等待与已就绪却排队等待；不使用 IPC 直接判断抢占。
- 跨 NUMA 候选需要实际 CPU 落点、内存位置及可用的远端访存证据支持，CPU 所在 NUMA 变化本身不足以确认根因。
- 中断频率高不等于网卡处理跑满；还需同 CPU 的 IRQ/softIRQ/NAPI 耗时、队列活动、吞吐平台期和业务线程等待等证据。
- 不支持或未采集的数据记为缺失，并说明原因，不能用零代替。

| 差异现象 | 优先候选 | 下一步验证 |
| --- | --- | --- |
| 热线程持续接近单核容量，单位 IO CPU 成本增加 | 额外处理、切线程或拷贝等开销 | 对比热点栈与切换/IO，验证单项改动 |
| 业务线程 CPU 时间下降、运行队列等待上升，同核竞争者活跃 | 调度竞争或抢占 | 调度跟踪，隔离竞争者或改变绑定做 A/B |
| IPC 下降、cycles/IO 增加，局部性证据改变 | 缓存/内存等待，跨 NUMA 为候选之一 | 固定 CPU 与内存位置做单变量验证 |
| 写退化，网络处理 CPU 集中繁忙，远端返回等待增加 | 网卡队列/中断处理集中或与业务争核 | 分别验证队列/IRQ 分布与业务隔离 |

以上均是判断规则草案，不是实测结论。CPU 线索不足时继续保留设备、锁或 IO 等待方向。

## 采集节奏与开销

每轮 fio 先预热 30 秒，再正式测试 60 秒。每 3 秒一个观测区间：预热 10 个、正式测试 20 个，共 30 个区间；含初始基线则原始计数有 31 个端点。预热独立标记，不混入正式结果与每 IO 成本。

每个区间关联同期 guest 完成数与 IOPS、各具体线程的 PID/TID/生存期、上一个端点 CPU 与本次最后执行 CPU、实际区间 CPU 利用率、同窗 instructions/cycles/IPC、运行队列等待和迁移计数。按单调时钟的绝对采样期限调度，保存实际起止与有效时长，不能因为配置了 3 秒就把所有实测时长强写成 3 秒。

线程可以在区间内多次迁移。`/proc/<pid>/task/<tid>/stat` 的 CPU 字段是最后执行位置；端点相同不能证明区间内没有迁移。完整 CPU 驻留轨迹作为后续调度事件适配器扩展，当前页面不作此承诺。SMT 展示同物理核的其他逻辑 CPU 与其同窗负载，并保留 CPU 的 IRQ/softirq；拓扑共享和同时繁忙是观察证据，不能直接确认争抢根因。

各层时延、深度保留 `layers[]` 扩展，时延单位为 μs、深度为待处理数量，`scope` 声明层内统计范围。具体来源、计算口径和采集方法等用户补充后再接适配器；未提供数据时不猜测或填 0。

每次测试保存全程的基本时间线，在明确标记的稳态窗口采集 perf stat 和固定预算的 perf record。IPC 必须来自对应 3 秒区间的同一线程计数，不能将全轮平均 IPC 复制到每点。采集参数在基线与候选间保持一致；接入真实集群后先测量采集对 fio 的影响，再确定计数与栈采样的开销预算。

有退化或基础证据不足时，针对异常场景增加调度事件、IRQ/softIRQ 时长和 NUMA 等深入采集。普通 perf 热点描述正在运行的路径，调度事件用于区分就绪排队与阻塞等待。

guest、两台数据主机的窗口与 fio 阶段对齐；保存时钟偏差和采集起止时间，不能只凭不同机器的相似时间戳推断因果。退化阈值参考同场景历史波动，并通过重复测试确认。

## 页面先围绕一次版本排查组织

页面主线：**测试批次 → 下降场景 → 上一次/本轮对比 → 线程、CPU 与网络差异 → 候选原因与验证记录**。

先展示 fio 曲线和下降程度，再展示与同一时间窗口关联的线程 CPU/等待、热点栈、IPC/单位 IO 成本、CPU/NUMA 落点及网络处理。候选原因列出证据、不足与下一项实验；专家记录验证后是确认、否定还是仍待验证。

采集模块预留 thread_cpu、perf_stat、perf_record、scheduler、numa、network_irq 等独立适配器。统一产物包含 run_id、主机、角色、时间窗口、指标单位、原始文件和质量状态；以后增加 NVMe 中断、其他协议前端或其他事件，不改变既有 fio 结果与诊断记录。
